## Дополнение 3 (09.09): пробная запись = пустые dates, без флага в бакете

Решение пользователя: при `lr_stage_probe` сервер пишет
`{"vk_user_id": "...", "dates": []}` — пустые даты естественно исключают
запись из `due` (флаг в записи не хранится). Дырка, закрываемая вместе:
`updatePushDates` шлёт `vk_subscribe` при изменении базы БЕЗ флага и
перезаписал бы запись реальными датами → таймер получил бы код 1 и удалил.

1. **push.py `_vk_subscribe`**: при `body.get("lr_stage_probe")` —
   `rec = {"vk_user_id": uid, "dates": []}` (флаг не пишем).
   В `_run_daily_vk` проверку `s.get("lr_stage_probe")` оставить —
   старые записи с флагом продолжают пропускаться.
2. **index.html**: `VKPUSH_PROBE` (localStorage): ставится в `togglePushVk`
   при пробной подписке (`!granted`), снимается при `granted` и при 🔕
   (вместе с `VKPUSH_KEY`); `updatePushDates` добавляет
   `lr_stage_probe: 1` в payload при `VKPUSH_PROBE === "1"`.

Запись в бакете после пробной подписки:
`{"vk_user_id": "123456789", "dates": []}`.

## Проблема

`_run_daily_vk` шлёт по одному подписчику: `sleep 0.34` + HTTP RTT (~0.2-0.3 c)
на каждого → дедлайн `VK_BUDGET=22 c` пропускает большую часть, отложенные
уезжают в `pending` на **следующий день** — напоминание о дне рождения
«завтра» бессмысленно. **Решение пользователя: недоставленные напоминания
НЕ переносятся на завтра** — механизм `pending` удаляется целиком; не
доставил в день даты — не доставишь (потеря принимается осознанно).

По официальной доке `notifications.sendMessage`: `user_ids` — до **100
идентификаторов за один вызов**, ответ — массив пер-пользовательских
статусов `{user_id, status, error: {code, description}}`. Пачки по 100
сводят рассылку к 1-3 HTTP-запросам, так что потери будут редкими.

Отвергнутый вариант из примера пользователя (`execute` + VKScript по 25):
URL не API (`https://vk.com`), текст интерполируется в VKScript (инъекция),
`return 1` теряет статусы доставки. Прямой `user_ids` проще и документирован.

## Изменения (только `LunarReturns/function/push.py`)

1. **`_vk_send_chunk(user_ids)`** вместо `_vk_send(user_id)`:
   - `user_ids` = список uid через запятую (≤100);
   - `random_id` — один на вызов (`random.randint(0, 2**31-1)`, защита от
     дублей в час);
   - парсинг ответа: топ-уровневый `error` → `fatal: код` (системная —
     стоп рассылки); `response[]` → по каждому запрошенному uid:
     `status: true` → ok; пер-код `1`/`4` → disabled (удаление);
     `2`/`3` → limit (fails не растёт); прочее → fails++.
     Отсутствие uid в `response` → failed (fails++);
   - сетевые ошибки (`URLError`/`OSError`) → весь чанк failed (не вина
     подписок, fails не растут);
   - возвращает разбиение запрошенных uid на категории:
     `{ok: [], disabled: [], limit: [], failed: []}` + `fatal: "..." | None`.
2. **`_run_daily_vk(deadline=None)`** — цикл по чанкам:
   - `due` — ТОЛЬКО подписки с датой на сегодня (`test:1` исключены);
     сортировка и механика `pending` **удаляются**: невыполненное не
     переносится на завтра (решение пользователя);
   - чанки по `VK_CHUNK=100`; перед каждым чанком проверка `deadline`
     (monotonic) — не успели → остаток `due` просто считается failed/lost
     (в лог), отправка прекращается;
   - после ответа: ok → снять `fails`; disabled (1/4) → удалить подписки
     этих uid; limit (2/3) → failed; прочее → `fails++`, удаление по
     `VK_MAX_FAILS`; fatal → прервать чанки, остаток — failed/lost;
   - `time.sleep(VK_SEND_PERIOD)` между чанками (RPS); внутри чанка пауз нет;
   - возврат: `{"vk_sent", "vk_failed", "vk_lost"}` (lost — не влезли в
     бюджет/не попали в ответ).
3. **`_run_daily(deadline=None)` (web-push)** — та же отмена переноса:
   `due` только по дате; дедлайн/ошибки → failed (потеря), никакого
   `pending`; 404/410 — удаление; битый endpoint/VAPID — failed.
   Механика `pending` из web-ветки тоже удаляется.
4. **Константы**: `VK_SEND_CAP`/`VK_SEND_PERIOD` → `VK_CHUNK = 100`
   (максимум `user_ids` API); `VK_SEND_PERIOD = 0.34` остаётся как пауза
   между чанками. `VK_MAX_FAILS`, `VK_BUDGET`, `PUSH_WEB_BUDGET` — без
   изменений.
5. **`_vk_random_id(user_id)`** удалить (один random на чанк; дедуп VK
   действует час, завтрашних повторов больше нет по решению выше).

## Сохраняется без изменений

- test-подписки (`test:1`) исключаются из `due`;
- семантика ошибок: disabled (1/4) — удаление, limit (2/3) — без fails,
  fatal — стоп без fails (после отмены pending — просто failed/lost);
- дедлайн-бюджеты в `handler` (`PUSH_WEB_BUDGET`/`PUSH_VK_BUDGET`);
- `vk_unsubscribe`, `VK_PUSH_CONSENT`, фронт — не затрагиваются.

## Риски

- Недоставленное (дедлайн, сетевые ошибки, лимиты 2/3, fatal) теряется
  безвозвратно — осознанное решение пользователя: напоминание «завтра»
  бессмысленно. Пачки по 100 делают потери редкими.
- Батчинг по 100 при суточном лимите VK (код 3): значительная часть чанка
  может попасть в limit — они фиксируются как failed.
