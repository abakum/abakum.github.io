# Ускорение облачного обмена ВК: упаковка базы по 50 записей на ключ

## Проблема

`vkDbPut` (LunarReturns/index.html:2747) делает до 990 последовательных
`await VKWebAppStorageSet` — мобильный клиент троттлит bridge-вызовы,
сохранение занимает десятки секунд. `vkDbClear` (:2821) пробегает все ключи
(`GetKeys` + затирание каждого). `vkDbGet` (:2763) читает все 990 ключей
даже когда используется 20.

## Решение (без хранимых процедур)

Новая схема хранения: один ключ VK Storage = **массив записей**. Лимит
значения — 4096 байт, поэтому чанк формируется строго по байтовому бюджету.
Мелкие записи («Я» + дата ≈ 30 байт) дают до сотни записей на ключ, крупные
(имя 64 символа + h/m ≈ 200 байт) — ~20; отдельного лимита количества записей
и ограничения длины имени не вводим (длина имени остаётся maxlength="64",
как сейчас).

- **989 записей → порядка 10–20 ключей → столько же вызовов
  `VKWebAppStorageSet`** вместо 990. Хранимые процедуры ВК не нужны.
- **Счётчик ключей**: в служебном ключе `"cnt"` хранится число занятых
  ключей данных (строка-число). Позволяет:
  - `vkDbGet`: прочитать `"cnt"`, запросить `VKWebAppStorageGet` только
    ключей `"0".."cnt-1"` (один вызов, но меньше трафика);
  - `vkDbPut`: затирать хвост только от старого `cnt` до нового (не все 990);
  - `vkDbClear`: затереть только `"0".."cnt-1"` и `"cnt"`.
- Паковка чанков — **по фактическому байтовому размеру**: записи добавляются,
  пока `byteLen(JSON.stringify(chunk)) + byteLen(next) ≤ 4096`. Переполнение
  ключа невозможно: имя ≤64 (~128 байт) + остальные поля < 200 байт.

## Совместимость со старой схемой

Старые данные: ключи `"0".."N"` содержат одиночные объекты записей `{...}`;
новые — массивы `[{...}, ...]`. Формат различается первым символом значения
(`[` vs `{`).

- **Чтение**: если `"cnt"` отсутствует — легаси-путь: читать `"0".."989"`
  одним `VKWebAppStorageGet`, распознавать оба формата, объединять.
  Если `"cnt"` есть — читать только `"0".."cnt-1"` (массивы).
- **Запись**: всегда новая схема; после записи `"cnt"` = число ключей.
  Первое сохранение автоматически мигрирует облако.
- **Очистка**: если `"cnt"` нет — разовый легаси-проход через
  `vkStorageGetKeys()` (как сейчас), затем пишем `"cnt"` при следующем save.

Ключ `"cnt"` не числовой — с данными не пересекается; в `vkDbClear` его
затирать; ключи `lr_s_*` (настройки) по-прежнему не трогаем.

## Изменения в index.html

1. Константы возле `LR_S_BLOB_KEY`: `VK_DB_CHUNK_BYTES = 4096`,
   `VK_DB_CNT_KEY = "cnt"`, лимит записей — прежние 989 (⇒ ≤ ~30 ключей,
   далеко от 1000 ключей на пользователя).
2. Хелперы паковки: `vkDbChunks(records)` → массив строк (JSON-массивов)
   с бюджетом байт/количества.
3. `vkDbPut` (:2747):
   - прочитать текущий `"cnt"` (один `vkStorageGet(["cnt"])`; при отсутствии
     — легаси: `vkStorageGetKeys()` + чтение старых данных уже сделает merge
     на стороне get; для put достаточно старого числа ключей, fallback 0 →
     тогда хвост не чистим, а «мусор» старой схемы затирается легаси-очисткой
     ниже — см. п.6);
   - разбить `db` на чанки, записать последовательно (~20 await вместо 990);
   - затереть хвост `for i in [chunks.length, oldCnt)`: `vkStorageSet(i, "")`;
   - записать `"cnt"` = chunks.length;
   - статус с числом записей и ключей.
4. `vkDbGet` (:2763):
   - прочитать `"cnt"`; если есть — запросить `"0".."cnt-1"`; иначе — легаси:
     `"0".."989"` и распознавание одиночных записей;
   - парсинг: значение начинается с `[` → `JSON.parse` массив, проверить
     `every(validRecord)` каждого элемента; с `{` → одиночная запись
     (легаси); ошибка — прежнее сообщение про «не JSON»;
   - дальше логика merge/seed/confirm — без изменений.
5. `vkDbClear` (:2821):
   - если `"cnt"` есть — затереть `"0".."cnt-1"` и `"cnt"` (~21 вызов);
   - если нет — прежний проход `GetKeys` (легаси), плюс явное удаление `"cnt"`
     на всякий случай.
6. Легаси-«хвост»: если при put старый `cnt` не найден, а в облаке есть
   старые одиночные записи — после успешной новой записи выполнить разовую
   легаси-очистку числовых ключей (по `GetKeys`), чтобы старые записи не
   удваивались при следующем легаси-чтении. Достаточно одного раза:
   пишем `"cnt"` сразу, последующие put чистят только хвост.
7. `vkDbGet`/`vkDbPut` — статус-сообщения упоминать новую упаковку
   («записей N, ключей K»).
8. QR-экспорт/импорт, localStorage, idb — без изменений.

## Риски

- Бюджет считается по факту (`byteLen` уже есть в коде (:1193)) и проверяется
  до добавления каждой записи — лимит VK Storage 4096 на значение соблюдается
  точно, запас не нужен. Граничные случаи: чанк из записей с именами по
  64 символа и чанк мелких записей — оба ≤ 4096 байт.
- Гонка put при двух устройствах: как и раньше, последнее сохранение
  выигрывает; `"cnt"` согласован с записанными ключами, т.к. пишется последним.
- Частично записанная база (обрыв сети): `cnt` не обновился → следующее
  чтение видит старое состояние либо легаси-мусор; приемлемо (как раньше),
  merge-диалог смягчает.
- Старые клиенты (старая версия приложения) прочитают новые массивы как
  «не JSON»-ошибку записи. Обновление публикуется одновременно; допустимо.

## Валидация

1. Локально: `vkDbChunks` — юнит-проверки вручную в консоли: 989 записей →
   ≤20 чанков; имена 64 символа → чанки не превышают 4096 байт; пустая база →
   0 чанков, cnt=0.
2. Мини-апп, база ~100 записей: замер времени сохранения до/после;
   `vkStorageGetKeys()` показывает ~`cnt`+1 ключей.
3. Миграция: облако со старыми одиночными ключами → загрузка (get) читает
   легаси, сохранение (put) переписывает в новую схему, повторная загрузка
   читает по `cnt` и данные совпадают (без дублей).
4. Отзыв согласия (vkDbClear): затёрты только `"0".."cnt-1"` + `"cnt"`,
   `lr_s_blob` не тронут; в легаси-режиме — все числовые ключи.
5. Граничные 989 записей — сохранение/загрузка без ошибок, время заметно
   меньше текущего.
