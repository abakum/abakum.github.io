# ВК-пуши LunarReturns через существующую функцию Яндекса + автотап при открытии

## Ответ на исходный вопрос

Да, ВК-версия может получать пуши, но механика отличается от веб-версии:

- **Web Push в мини-аппе ВК невозможен в принципе**: в вебвью ВК нет Service Worker/PushManager (уже учтено: `vkminiapp`-ветки в index.html:1299-1311, 1767, 1775, 1805).
- Вместо этого — **ВК-нативные уведомления**: разрешение у клиента через vk-bridge (`VKWebAppAllowNotifications`/`VKWebAppDenyNotifications`, оба есть в бандле 3.0.2), отправка — **только сервером** через VK API с сервисным ключом.
- Отправку размещаем в существующей функции `lunarreturns-push` (репо `abakum/LunarReturns`): её таймер (09:00 МСК) и S3-хранилище уже работают в проде; отправка ВК-уведомления = HTTPS-вызов api.vk.com. VK Cloud Functions — задокументированная альтернатива, не делать.
- Текст уведомления формирует сервер, клиентский код «в момент пуша» в ВК не выполняется (нет SW). Сервер знает только MM-DD → текст только общий («Сегодня есть поводы — откройте приложение»), имена приложение показывает локально при открытии.

## Решения (зафиксировано с пользователем)

1. **Данные**: сервер хранит только `{vk_user_id → [MM-DD…]}`. MM-DD — обезличено; имена устройство не покидают. **Чекбоксы согласия: в веб-режиме (Яндекс) — один** (существующий `pdConsent`, index.html:172-175, только база событий, не меняется), **в ВК-режиме — два**: `pdConsent` + новый **`pdPushConsent`** — согласие на хранение `vk_user_id` + MM-DD в Яндекс Облаке для отправки уведомлений (текст: «Разрешаю хранить ВК-ид и даты (без года) в облаке Яндекс для отправки уведомлений»), свой localStorage-ключ `lunarreturns.pdPushConsent`, отображается только в ВК-режиме (в веб-режиме скрыт, Web Push хранит лишь идентификатор экземпляра браузера). Шифрование at-rest решено не вводить (мера защиты, не основание обработки по 152-ФЗ). **🔔 в ВК-режиме показывается только при push-согласии**; без него `vk_subscribe` не отправляется. **Отзыв push-согласия стирает подписку** этого ВК-ида: POST `vk_unsubscribe` + снятие флага `lunarreturns.vkpush` (базу событий `vkDbClear()` не трогает — за неё отвечает первый чекбокс).
2. **UX при открытии (в любом режиме, ВК и веб)**: если сегодняшняя MM-DD (МСК) есть в локальной базе — автотап по первой совпавшей строке (как `hashSelect()` → `row.click()`, index.html:1428-1435); иначе — как сейчас `renderNow()` («луна», index.html:724-737). Явный `#N` в хэше приоритетнее автотапа. **Автотап — раз в день**: ключ `localStorage["lunarreturns.autotap"]` = сегодняшняя дата МСК (`YYYY-MM-DD`); ставится только при фактическом срабатывании автотапа (если совпадения нет — флаг не ставится, повторные проверки за день бесплатны и без UX-эффекта). При сработавшем `#N` флаг не трогаем. Смена origin у ВК-хостинга обнуляет localStorage — просто один повторный автотап на новый origin, приемлемо. **Порядок поиска: сначала `db`, если не нашли — религиозные дни** (`daysEntries()` при установленном `dayKind`); нашли там — «тап по яйцу» (`toggleReligionBtns()`, index.html:956-976): включается религиозный режим, `buildDays()` строит окно от сегодня (index.html:1082-1086) и сегодняшняя строка — первая в списке. Совпадение и в db, и в днях → выигрывает db, яйцо не тапаем. `dayKind` пуст → «луна».
3. **Инфраструктура — расширить функцию `lunarreturns-push`** (push.py). VK Cloud Functions остаётся альтернативой (не делать).
4. Крайние случаи: 28.02 невисокосного года матчит и «02-29» (паритет с sw.js:114-116 и push.py:106-112; для дней достаточно фактического MM-DD); несколько совпадений — клик по первому; религиозные дни участвуют во второй очереди автотапа (п.2) и остаются в датах пушей.

## Как устроено серверное хозяйство (факты из кода)

- Репо `abakum/LunarReturns`: `function/push.py` (+ `handler.py` с `_presign`/`_response`), `deploy.sh`, `.github/workflows/deploy.yml` (workflow_dispatch).
- Маршрутизация `push.handler` (push.py:199-214): `OPTIONS` → 200; без `httpMethod` (таймер `lunarreturns-push-timer`, cron `0 6 ? * * *`) → `_run_daily()`; иначе — проверка `Origin == ALLOWED_ORIGIN` (env, дефолт `https://abakum.github.io`; в env push-функции deploy.sh его не передаёт) и действия `subscribe`/`unsubscribe`.
- Хранилище: бакет `lunarreturns`, один ключ `push/subscriptions.json` (список веб-подписок). CORS-ответ функции: `Access-Control-Allow-Origin: *`.
- Секреты: GitHub Secrets репо `abakum/LunarReturns` → workflow → env `deploy.sh` → `yc serverless function version create --environment` (вывод в CI глушится, deploy.sh:104-116). VAPID так и ходит; локально — `.vapid.env`.

## Секреты ВК в функции Яндекса (ответ на вопрос пользователя)

Да, безопасно, по тому же пути, что `VAPID_PRIVATE`:

- `gh secret set VK_APP_SECRET -R abakum/LunarReturns` (защищённый ключ приложения — проверка `sign` launch-параметров) и `VK_SERVICE_TOKEN` (сервисный ключ — отправка уведомлений).
- `deploy.yml` прокидывает их в шаг Deploy как env; `deploy.sh` добавляет в `--environment` push-функции. Значения не попадают в код, логи CI (вывод `version create` заглушён) и оба публичных репо.
- Обычные env-переменные хранятся в метаданных версии функции открыто (видны в консоли при доступе на чтение каталога) — приемлемо для личного каталога; строгое усиление — Lockbox с подстановкой в env при вызове (`--secret environment-variable=…,lockbox-secret-id=…`), опционально.
- `sign` — единственный барьер против подделки `vk_subscribe` (URL функции публичен в index.html), поэтому `VK_APP_SECRET` критичен. Не логировать env в функции.

## Вердикт-риски (проверить до кода)

- **Метод отправки ВК-уведомлений**: README упоминает `execute.push`; классическая альтернатива — `secure.sendNotification`. Сверить с актуальной докой dev.vk.com; изолировать в одной функции `_vk_send`.
- **Формула `sign`** (md5 по белому списку launch-параметров, отсортированных `key=value` без разделителей + защищённый ключ) — сверить точный алгоритм и белый список параметров с докой.
- Лимиты ВК-уведомлений (частота, длина текста ~90 символов) и коды ошибок «уведомления отключены» (для автоочистки подписок).
- Origin из вебвью ВК (мобильный клиент может не слать Origin): проверку ослаблять осознанно — для vk_-действий защита = sign, origin-чек — вспомогательный.

## Задачи

### A. Клиент — `abakum.github.io/LunarReturns/index.html`

1. **Автотап при старте (оба режима), раз в день**: после `hashSelect()` (строка 1823) — если `#N` не сработал (пусть `hashSelect` вернёт boolean), хэш не миграционный (`lr_db`/`lr_migrate`/`lr_fail`, строки 253-290) и `localStorage["lunarreturns.autotap"] !== <сегодня YYYY-MM-DD по МСК>` — вычислить сегодняшние MM-DD по МСК (паттерн sw.js:90-92, плюс 02-28→02-29 невисокосный), затем по порядку: (а) первая запись `db` с `r.d.slice(5)` в матчерах → `row.click()` + `window.scrollTo(0,0)`; (б) иначе при непустом `dayKind` — сегодня в `daysEntries()` (index.html:992-999) → `toggleReligionBtns()` (religionMode на старте всегда выключен; яичный тап откроет список дней с сегодняшней строкой первой); в случае (а) или (б) записать флаг с сегодняшней датой; ни того ни другого — ничего, флаг не менять.
2. **ВК-ветка пушей** (тот же `PUSH_URL`, новых констант не нужно):
    - **Push-согласие**: новый чекбокс `pdPushConsent` рядом с `pdConsent` (только ВК-режим, паттерн `applyVkUi`/`applyPdConsent`): label + текст из п.1 Решений, ключ `lunarreturns.pdPushConsent`, хелпер `pushConsentGiven()` (паттерн `pdConsentGiven()`, index.html:1297-1299). Отзыв чекбокса: если активна пуш-подписка — confirm → POST `vk_unsubscribe` + снять флаг `lunarreturns.vkpush`; отменённый confirm возвращает галочку.
    - `refreshPushBtn` (1803): в ВК-режиме показывать кнопку **только при push-согласии** (`pushConsentGiven()`), состояние из `localStorage["lunarreturns.vkpush"]`; снять согласие → кнопка скрывается.
    - `togglePush` (1773): ВК-ветка (достижима только при согласии) — `vkBridge.send("VKWebAppAllowNotifications")` → POST `PUSH_URL` `{action:"vk_subscribe", launch_params: {все vk_* из location.search + sign}, dates: allPushDates()}` → флаг=1. Отключение: POST `vk_unsubscribe` + `VKWebAppDenyNotifications` → флаг снят. Ошибки — `status()`.
    - `updatePushDates` (1765): ВК-ветка — если флаг и push-согласие, повторно POST `vk_subscribe` с датами.
3. README (страницы-репо): заменить абзац «Пуши (🔔) в мини-аппе пока отключены» (README.md:134-135) на описание механизма и автотапа.

### B. Сервер — репо `abakum/LunarReturns`

1. **`function/push.py`**:
   - Новые действия `vk_subscribe`/`vk_unsubscribe`: проверить `sign` (по `VK_APP_SECRET`, алгоритм из доки); хранить `[{vk_user_id, dates}]` в **отдельном ключе** `push/vk_subs.json` (переиспользовать `_load_subs`/`_save_subs` с параметром ключа); санити дат как в `_subscribe` (`MAX_DATES`, `DATE_RE`). Без `VK_APP_SECRET` → 500 «not configured» (паттерн `_run_daily`, push.py:141-142).
   - `_run_daily()` (или соседняя `_run_daily_vk` из того же таймер-входа): today из `_today_md()`, для due-подписок `_vk_send(vk_user_id)` (VK API, `VK_SERVICE_TOKEN`, urllib, без новых зависимостей), троттлинг ~3 rps, ошибки логировать; «уведомления отключены» → удалить подписку (аналог 404/410, push.py:160-163).
   - `_origin_allowed`: разрешить текущий `ALLOWED_ORIGIN` + origin'ы хостинга ВК `^https://(prod|stage)-app54746591-[a-z0-9]+\.pages\.vk-apps\.(ru|com)$` (паттерн = `LR_ORIGIN_RE`, index.html:239); отсутствующий Origin (вебвью) не считать ошибкой для vk_-действий.
2. **`deploy.sh`**: в `deploy_push_version` (строки 127-131) добавить `VK_APP_SECRET`/`VK_SERVICE_TOKEN` в env (при отсутствии — warn и деплой без них; vk_-действия ответят 500). Секреты как VAPID: GitHub Secrets; локально можно расширить `.vapid.env`-паттерн (напр. `.vk.env`).
3. **`.github/workflows/deploy.yml`**: в шаг Deploy добавить env `VK_APP_SECRET: ${{ secrets.VK_APP_SECRET }}`, `VK_SERVICE_TOKEN: ${{ secrets.VK_SERVICE_TOKEN }}`. Новых шагов-проверок не нужно (паттерн «Ensure VAPID keys» опционально продублировать warning'ом).
4. Порядок выката: сначала функция (B), потом клиент (A) — до появления `vk_subscribe` в проде клиент должен не слать его (ветка по флагу включения).

### Альтернатива (не делать): VK Cloud Functions

Тот же код отдельной функцией в VK Cloud (провижининг: проект, Object Storage, таймерный триггер) — только если расширение функции Яндекса окажется неприемлемым.

## Валидация

- **Функция**: curl `vk_subscribe` с реальными launch params мини-аппа (sign уже в них) → 200, в бакете появился `push/vk_subs.json`; подделанный sign / чужой набор параметров → 403; curl с Origin `https://prod-app54746591-x.pages.vk-apps.ru` → не 403 по origin. Отправка: `yc serverless function invoke lunarreturns-push` (внутри `yc` контекста) или временный env-флаг dry-run — реальный пуш придёт администратору; повтор при отключённых у пользователя уведомлениях → подписка удалена из `vk_subs.json`.
- **Клиент-автотап**: Pages-версия — при совпадении даты открывается запись, без совпадения «луна»; `dayKind` установлен, в db совпадения нет, сегодня есть в днях → открыт религиозный режим со списком дней (сегодняшняя строка первая); есть и db-, и день-совпадение → показана запись db; `dayKind` пуст → «луна»; повторное открытие в тот же день → «луна» (флаг сработал), после удаления `lunarreturns.autotap` → автотап снова; `#N`, OAuth- и миграционные хэши не сломаны; 28.02/29.02 проверить подменой даты в базе.
- **E2E в dev-мини-аппе** (vk.ru/app54746591): без push-согласия 🔔 скрыт; с согласием → разрешение → подписка → дата=сегодня → срабатывание таймера/ручной invoke → пуш в ВК → тап → автотап показывает запись с именем; отзыв push-согласия при активной подписке → `vk_subs.json` без записи, 🔔 скрыт, флаг снят, база событий и первый чекбокс не затронуты.
- **Регресс веба**: `subscribe`/`unsubscribe` и таймер для веб-подписок работают как раньше (sw.js не трогаем); smoke-test deploy.sh (пустой POST → 4xx) зелёный.
