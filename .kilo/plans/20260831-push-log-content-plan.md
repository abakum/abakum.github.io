# План: показывать фактическое содержимое пуша в журнале

## Проблема
Сегодня пуш отработал корректно (уведомление показано), но запись журнала выглядит так:
```
31.08.2026, 09:00:23 — без payload — db:2 days:0 — показано
```
По записи нельзя понять, ЧТО именно было показано (какие имена из `db`/`days` попали в тело уведомления). Нужно фиксировать в журнале фактическое содержимое.

Решение: заменить бесполезное поле payload (всегда пустое) на поле с реальным содержимым уведомления. Payload не протоколируем вовсе.

## Контекст
- [`LunarReturns/sw.js:109`](../LunarReturns/sw.js:109) — обработчик `push`: читает `db`/`days`, собирает `all = labels.concat(days)` и показывает `showNotification("Сегодня", { body: all.join(", "), tag: "bd" })`.
- Переменная `all` доступна на момент записи лога — содержать в записи фактические элементы можно без изменения бэкенда (внешняя Яндекс Cloud Function, `PUSH_URL`).
- [`LunarReturns/index.html:958`](../LunarReturns/index.html:958) — `renderPushLog()` форматирует строки журнала.
- Бэкенд (`PUSH_URL`) в репозитории отсутствует, менять его не нужно.

## Изменения

### 1. `LunarReturns/sw.js`

**Бамп кэша**: `CACHE = "lunarreturns-v6"` → `"lunarreturns-v7"` (SW меняется — должен обновиться у установленных PWA).

**В `push`-обработчике**:
- удалить блок чтения payload (`let payload … try/catch … e.data.text()…`);
- в записи журнала заменить поле `payload` на `body` с фактическим содержимым:
```js
await idbPutLog({
    t: new Date().toLocaleString("ru-RU", { timeZone: "Europe/Moscow" }),
    db: nDb,
    days: nDays,
    shown: shown,
    body: all.join(", ").slice(0, 200)   // новое: что было бы/было показано
});
```
- `all` уже в области видимости; при отсутствии совпадений будет `""` (пусто);
- срез до 200 символов защищает от переполнения журнала при многих записях;
- старые записи без поля `body` остаются валидными — не ломаем чтение.

### 2. `LunarReturns/index.html`

В `renderPushLog()` убрать флаг payload и вывести содержимое уведомления отдельной строкой без префикса. Сохранить совместимость со старыми записями (без `body`).

Формат вывода (пример):
```
Журнал пушей:
31.08.2026, 09:00:23 — db:2 days:0 — показано
Иван 17, Иван+Мария 17 розовая
```
Логика построения строки:
- основная строка: `t — db:N days:N — показано/НЕ показано`;
- если `r.body` есть и непуст — добавить следующую строку с самим содержимым `<r.body>` (без префиксов и отступов);
- если `r.body` есть, но пуст (нет совпадений) — `(пусто)`;
- если поле `body` отсутствует (старая запись) — ничего добавлять (флаг payload больше не выводим).

## Риски / заметки
- Запись пишется в любом исходе (структура `push`-обработчика не меняется — только удаляем payload и добавляем поле).
- Падение при `e.data` больше не актуально (payload не читаем вовсе); `body` строится из локальных данных.
- `db`/`days` дают счётчики, `body` — состав; дублирование допустимо.

## Валидация
1. `npx serve LunarReturns`, открыть страницу, DevTools → Application → Service Workers → обновить → новый SW (v7).
2. Положить в IndexedDB ключ `"db"` с 1–2 записями на сегодня МСК, `"days"` — с одним событием на сегодня.
3. Application → Service Workers → кнопка «Push»: уведомление «Сегодня», в журнале под строкой журнала отдельной строкой идёт список имён (`Иван 17, Иван+Мария 17 розовая`), без упоминания payload.
4. Кейс «нет совпадений»: уведомление не показано, журнал `НЕ показано` + строка `(пусто)`.
5. Проверить старую запись (без `body`): строка рендерится без доп. строки содержания, без ошибок.
