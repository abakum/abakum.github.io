# LunarReturns: перезапуск автопоиска именинника после суток в фоне

## Задача

Если после скрытия мини-аппа/страницы в фон и возврата наступили новые сутки (по МСК),
выполнить тот же стартовый автопоиск, что и при запуске приложения. Сигналы возврата —
`document.visibilitychange` (браузеры, iframe) и `VKWebAppViewRestore` (нативные клиенты ВК),
см. https://dev.vk.com/ru/bridge/background-mode.

## Решения (согласованы с пользователем)

1. **Полный «перезапуск старта»**: `renderList()` + `renderNow()` + `autoTapToday()` —
   ровно то, что видно при повторном открытии приложения в новые сутки (иначе без
   именинника останется вчерашняя строка «Сейчас» или вчерашний выбранный результат;
   заодно обновятся возрасты в списке 1 января).
2. **Несохранённый ввод в форме — защита**: если форма «грязная» (незакрытые модальные
   диалоги тоже считаем занятостью UI) — пропустить перезапуск и НЕ фиксировать смену
   даты: повторная проверка произойдёт при следующем скрытии/возврате в те же сутки.

## Контекст кода (LunarReturns/index.html)

- Стартовая последовательность: строки 3400–3414 — `loadDb(); loadDayKind(); renderList();
  renderNow(); … if (!hashSelect()) autoTapToday(); …`
- `autoTapToday()` — строка 2582: ищет сегодняшние MM-DD (МСК) в базе, выбирает первую
  запись (`selectRecord` + `startEdit`), иначе при совпадении религиозного дня открывает
  кнопки конфессий.
- `mskToday()` — строка 1695 (const-стрелка, TDZ): текущая дата по МСК.
- `todayIdxs()`/`todayMds()` — строки 2568–2580: считаются заново при каждом вызове,
  отдельного состояния дня не требуют.
- Уже существующие хуки возврата (сейчас только обновляют тему):
  - `document.addEventListener("visibilitychange", …)` — строки 782–784;
  - `vkBridge.subscribe` → ветка `VKWebAppViewRestore` — строки 794–796.
- Android-клиент ВК через 3 секунды в фоне приостанавливает JS — таймеры не вариант,
  сравнение дат при возврате корректно.

## Изменения (один файл: `LunarReturns/index.html`)

1. **Запомнить день последнего автопоиска.** Сразу после `mskToday()` (~строка 1698):
   ```js
   // День (МСК) последнего выполненного автопоиска именинника: обновляется
   // при старте и в checkDayRollover() при возврате из фона в новые сутки.
   let lrLastDay = mskToday().join("-");
   ```
   Инициализация на месте объявления (после TDZ-определения `mskToday`) — события
   `visibilitychange`, пришедшие до конца исполнения скрипта, не дадут ложного
   «перевода суток».

2. **Хелперы рядом с `autoTapToday()`** (после строки 2594):
   - `lrFormBusy()` — true, если открыт `#confirmOverlay`/`#pasteOverlay`
     (classList.contains("open")), либо в форме несохранённый ввод:
     - при `editingIdx >= 0` и существующей `db[editingIdx]` — любое из полей
       `fName`, `fDate`, `fHour`, `fMin` отличается от того, что записал бы
       `startEdit(i)` (`db[i].n`, `db[i].d`, `"h" in db[i] ? String(db[i].h) : ""`,
       аналогично `m`), либо `fCity !== ""` (startEdit сбрасывает город в "");
     - иначе (режим добавления) — любое из полей `fName`, `fDate`, `fHour`,
       `fMin`, `fCity` непустое.
     Сравнения строковые: `.value` инпутов — строки (число `0` → `"0"`).
   - `checkDayRollover()`:
     ```js
     function checkDayRollover() {
         const today = mskToday().join("-");
         if (today === lrLastDay) return;      // те же сутки — ничего не делаем
         if (lrFormBusy()) return;             // несохранённый ввод: повторим при следующем возврате
         lrLastDay = today;                    // фиксируем только при успешном прогоне
         renderList();
         renderNow();
         autoTapToday();
     }
     ```
     Идемпотентно: двойной всплеск событий (visibilitychange + VKWebAppViewRestore
     приходят вместе) обрабатывается один раз — второй вызов видит уже обновлённый
     `lrLastDay`.

3. **Подключить к хукам возврата:**
   - в visibilitychange-обработчике (строка 783): после `refreshThemeOnReturn()`
     добавить `checkDayRollover();`;
   - в ветке `VKWebAppViewRestore` (строка 794–796): так же, после
     `refreshThemeOnReturn()` (комментарий «избыточно с visibilitychange…» уточнить).
   Оба хука выше по коду, чем определения: вызовы асинхронны (события), function
   declarations hoisted — TDZ `mskToday`/`lrLastDay` к моменту вызова не актуален.

## Явно НЕ делаем (вне скоупа)

- `loadDayKind()`, пуши (`updatePushDates`), `vkRestoreCloud()`, PTR-reload —
  не трогаем: пользователь просил только поиск именинника «как при старте».
- Периодические таймеры проверки дня: не нужны (JS в фоне всё равно стоит).
- `location.hash` при возврате: не обрабатывается — стартовый приоритет `#N`
  не меняется.

## Риски

- `renderNow()` затирает текущий выбранный результат — принято (это паритет со
  стартом), срабатывает только при реальной смене суток.
- Всплеск двух событий возврата — покрыт идемпотентностью.
- `lrFormBusy()` не сравнивает `fCity` с записью (startEdit всегда кладёт "") —
  это сознательно: непустой город в форме всегда означает ручной выбор.

## Валидация (вручную, сборка не нужна — НЕ запускать `npm run build`)

1. Открыть приложение (локальный сервер или stage): зона результата — «Сейчас».
2. В консоли: `lrLastDay = "2000-01-01"; checkDayRollover();` — без изменений
   (сутки совпали с текущими), без мерцания.
3. Добавить запись с сегодняшним MM-DD (МСК), затем
   `lrLastDay = "2000-01-01"; checkDayRollover();` — результат переключился на
   эту запись, форма заполнена ею (как при старте), кнопки 🔼🔽 активны при
   нескольких именинниках.
4. Убрать из формы имя (или очистить поля), набрать текст без сохранения,
   `lrLastDay = "2000-01-01"; checkDayRollover();` — форма сохранена, автопоиск
   пропущен; повторный вызов после очистки формы — автопоиск выполняется.
5. Скрыть/показать вкладку (десктоп) в те же сутки — действий нет; в нативном
   клиенте ВК (Android/iOS stage) свернуть/развернуть — смена суток проверяется
   на `VKWebAppViewRestore`.
6. Ночной сценарий: оставить открытым через полночь по МСК, утром вернуть —
   увидеть автопоиск нового дня.
