# План: светлая вспышка темы при pull-to-refresh в тёмном режиме (нативный клиент ВК)

**Дата:** 2026-09-04
**Проект:** LunarReturns (мини-апп ВКонтакте)
**Задача:** При выполнении кастомного PTR (`location.reload()`) на тёмной теме в нативном клиенте ВК промелькивает светлая тема.

---

## 1. Симптомы (уточнены с пользователем)

- Вспышка появляется **только при кастомном PTR** в нативном WebView ВК.
- В браузере (Chrome) при обычном PTR — **нет вспышки**, потому что там работает браузерный (нативный) PTR, который держит старую страницу видимой во время reload и не перерисовывает её в светлом виде.
- Первая попытка фикса (ранний инлайн-скрипт в `<head>`, коммит `edb319e`) **не помогла**.

---

## 2. Диагностика по истории коммитов

Анализ `git log --oneline -30 -- LunarReturns/index.html` и diff ключевых коммитов:

| Факт | Детали |
|------|--------|
| `qr/qrcode.js` в `<head>` — изначально | `git log -S 'qr/qrcode.js'` пуст → не регрессия. |
| Персистентности темы в `localStorage` никогда не было | `git log -S 'localStorage.*theme'` пуст → тема всегда ставилась только JS в конце `<body>` (`applyTheme()`). |
| Структура `<head>` одинакова во всех последних коммитах | сеттер темы в head до сих пор отсутствовал; у меня добавлен только в `edb319e`. |
| До `ff9b03b` тёмный фон — сплошной `html.theme-dark { background:#7a6425 }` | `f712a22` (родитель градиента). |
| После `ff9b03b` — яркий градиент `linear-gradient(180deg,#0c1220…,#6e3b35)` | текущий код + такой же светлый градиент для light. |

### Корень проблемы

Механизм темы из плана `20260903-vk-theme-switch-plan.md`: в нативных клиентах источник — `prefers-color-scheme`, а конфиг темы от VK (`VKWebAppUpdateConfig` / `VKWebAppGetConfig`) приходит **асинхронно** после старта страницы; на Android System WebView медиазапрос к тому же **не пересчитывается сам** без фокуса/поворота.

При `location.reload()` из кастомного PTR в WebView на момент **первого кадра** сигнал темы ещё не тёмный:

1. `prefers-color-scheme` в WebView на старте навигации может быть светлым (тёмная схема приложения выставляется через мост чуть позже);
2. launch-параметр `appearance`/`vk_theme` в URL WebView **не гарантирован** (заметка в коде: «launch-параметр в вебвью не гарантирован»);
3. мой ранний head-скрипт из `edb319e` при отсутствии параметра тоже откатывался к `prefers-color-scheme` → светлый.

Итог: первый отрендеренный кадр — светлый, затем событие/конфиг моста вызывает `applyTheme()` → тёмный. Это и есть вспышка.

**Почему «стало заметно в последних коммитах»:** механизм был латентным (тема всегда применялась поздно), но градиентный коммит `ff9b03b` заменил незаметный плоский тёмно-золотой фон на яркий светлый градиент неба — теперь кратковременный светлый кадр бросается в глаза.

---

## 3. Решение

Сделать тему детерминированной на первом кадре, не зависящей от асинхронного сигнала WebView: **персистентность темы + чтение в head до первой отрисовки**.

### 3.1. Сохранять резолвнутую тему в `localStorage`

В `applyTheme()` (конец `<body>`) после вычисления `dark`:

```js
const THEME_KEY = "lunarreturns.theme"; // рядом с другими *_KEY константами
try { localStorage.setItem(THEME_KEY, dark ? "dark" : "light"); } catch (e) {}
```

`applyTheme()` вызывается из всех точек смены темы (старт, `change` медиазапроса, `VKWebAppUpdateConfig`, `GetConfig`, возврат в апп) → значение всегда актуально.

### 3.2. Ранний head-скрипт: читать `localStorage` первым

Доработать инлайн-скрипт из `edb319e` (тот же, синхронный, в `<head>` до `<style>`), чтобы приоритет стал:

1. `localStorage[THEME_KEY]` → `"dark"`/`"light"` (гарантия от FOUC на reload: значение пишется на предыдущей сессии того же origin);
2. launch-параметр `appearance`/`vk_theme`;
3. иначе `prefers-color-scheme`.

Классы `.theme-dark`/`.theme-light` и `meta[name="theme-color"]` — как уже сделано.

> `location.reload()` сохраняет тот же origin/`localStorage` → тёмная тема ставится до первого кадра. Это работает даже если launch-параметр отсутствует и `prefers-color-scheme` ещё светлый.

### 3.3. (Опционально) Перенос темы между origin VK-выкладок

Новая VK-выкладка получает **новый origin с пустым `localStorage`**. Чтобы тема пережила миграцию через `#lr_ls`:

- добавить `THEME_KEY` в `LR_LS_KEYS`;
- в `applyLsParams()` добавить ветку для `THEME_KEY`: принимать только `"dark"`/`"light"`.

Это закрывает сценарий «первый заход после деплоя в тёмном клиенте» (иначе там снова будет фолбэк на `prefers-color-scheme`).

### 3.4. (Опционально, вторично) Blank-кадр самого WebView

Если помимо светлой темы заметен и **белый кадр** в разрыве reload (независимо от страницы) — это фон самого WebView до загрузки HTML. Смягчить можно, гарантировав тёмный `background_color` в `VKWebAppSetViewSettings` (`dark ? "#0c1220" : ...`). Ограничение: событие не в схеме vk-bridge 3.0.2 и на части платформ игнорируется. Считаем вторичным, отдельно проверяем.

### 3.5. Про неудачный `edb319e`

Сам по себе ранний head-скрипт верен по идее и остаётся — его лишь **дополняем** чтением `localStorage` первым. Полный откат не нужен.

---

## 4. Что осталось проверить (нужен реальный нативный клиент ВК)

- [ ] Тёмная тема + кастомный PTR → reload: светлая вспышка исчезла.
- [ ] Светлая тема + кастомный PTR → reload: не становится тёмной.
- [ ] Смена темы в клиенте, затем PTR — новая тема переносится (не залипает старая из localStorage).
- [ ] Первый заход после новой VK-выкладки (новый origin) в тёмном клиенте — без вспышки (проверка 3.3).
- [ ] Браузер (vk.com): перезагрузка/PTR без регрессий, живая смена темы по `prefers-color-scheme` продолжает работать.
