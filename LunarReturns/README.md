# LunarReturns — VK Mini App

«Лунно-солнечные юбилеи» — статичное веб-приложение, разворачиваемое на
официальный хостинг VK Mini Apps через GitHub Actions (PWA с сервис-воркером —
это версия, публикуемая на GitHub Pages; в VK-сборку она не входит).

- `app_id`: **54746591**
- Конфигурация деплоя: [`vk-hosting-config.json`](./vk-hosting-config.json)
- Workflow: [`.github/workflows/deploy-lunarreturns-vk.yml`](../.github/workflows/deploy-lunarreturns-vk.yml)

## Подготовка (один раз)

1. Получите сервисный ключ мини-аппа.
   В панели разработчика: **Разработка → Ключи доступа → Сервисный ключ**.
   Либо скопируйте ключ, который печатает `vk-miniapps-deploy` при первом ручном
   деплое (он сохраняется в
   `~/.config/configstore/@vkontakte/vk-miniapps-deploy.json`).

2. Добавьте ключ как секрет репозитория GitHub:
   **Settings → Secrets and variables → Actions → New repository secret**.
   - Name: `MINI_APPS_ACCESS_TOKEN`
   - Value: ваш сервисный ключ

## Локальная сборка и проверка

```bash
cd LunarReturns
npm install
npm run build      # соберёт статику в папку build/
```

Содержимое `build/` — то, что уйдёт на хостинг VK.

## Запуск деплоя

В GitHub: **Actions → «Deploy LunarReturns to VK Mini Apps» → Run workflow**.

| Параметр     | Значение                                                    |
|--------------|-------------------------------------------------------------|
| `production` | чекбокс; отмечен — одним деплоем выложить сразу в dev и production |

### dev

Dev-деплой выполняется **при каждом запуске** (чекбокс не влияет) и полностью
автоматический, без подтверждения. В `vk-hosting-config.json` задано
`"update_dev": 1`: после выкладки VK сам переключает dev-URL приложения на новую
версию — вручную адрес переносить не нужно, `https://vk.ru/app54746591`
(внутри VK, для админов) сразу открывает свежую версию.

Стейджинг-адрес вида
`https://stage-app54746591-<hash>.pages.vk-apps.ru/index.html` при каждой
выкладке новый и **из CI скрывается** (в логе шага деплоя он маскируется,
в сводку запуска не выносится).

**Тестирование — внутри VK** (`https://vk.ru/app54746591`, для админов).
Прямой заход по stage-URL из обычного браузера открывает приложение как есть
(редирект на vk.ru/app убран): это нужно для ручного переноса базы между
версиями (см. «Хранение в VK Mini App»); вне VK-контекста VK-хранилище
недоступно, база локальна для браузера.

### Как устроены URL (VK API)

Отдельного API «сменить URL мини-аппа» у VK нет. Ссылки обновляются только
сервером в рамках задачи хостинга (`apps.getGoHostingUploadServer` → upload →
`apps.createGoHostingTask`), параметры которой управляют поведением:

- `environment` — `dev` и/или `production`; без `MINI_APPS_ENVIRONMENT`
  (или со значением, отличным от `dev`/`production`) утилита выкладывает обе
  среды **одной загруженной версией**;
- `update_dev` / `update_prod` — обновлять ли при выкладке дев-/прод-ссылки
  приложения (можно задать в `vk-hosting-config.json`);
- `test_group_name` — выложить версию в тестовую группу (ей обновится свой URL).

Новые URL приходят событием из очереди (`apps.subscribeToHostingQueue`) —
именно их утилита печатает как `URLs changed for dev|production`. При обычном
user-токене перевод прод-ссылок подтверждается через `apps.confirmDeploy` с
кодом администратора; сервисный ключ этого шага не требует. Назначить версии
произвольный (внешний) URL нельзя.

### production

Выполняется по чекбоксу `production` при запуске воркфлоу. В этом случае
деплой-шаг запускается с `MINI_APPS_ENVIRONMENT=all` (любое значение, кроме
`dev`/`production`, утилита трактует как «обе среды»): версия загружается
один раз, и VK обновляет сразу оба набора ссылок — и dev-, и прод-
(`"update_dev": 1`, `"update_prod": 1` в `vk-hosting-config.json`). Отдельный
dev-деплой при этом не выполняется — версия не загружается дважды. Код
подтверждения **не требуется**: сервисный ключ (`MINI_APPS_ACCESS_TOKEN`)
позволяет выкладку в production без подтверждения администратора (это
проверено тестовым воркфлоу).

Реальные production- и stage-URL **из CI скрываются** — в логе шага деплоя они
маскируются, поэтому доступны только в панели разработчика VK
(`Разработка → Мои приложения → Хостинг`).

> Альтернатива production-деплоя — локально:
> ```bash
> cd LunarReturns
> MINI_APPS_ACCESS_TOKEN=<ключ> MINI_APPS_ENVIRONMENT=production npm run deploy
> ```

## Хранение в VK Mini App

В мини-аппе база сохраняется в облако ВКонтакте через vk-bridge
(`VKWebAppStorageSet/Get`), без входа через Яндекс:

- **Одна запись базы = один ключ** `"0".."989"` (значение — JSON записи
  `{n, d}`). Ключи уникальны для каждого пользователя VK.
- Лимиты VK: значение ключа ≤ 4096 байт (записи хватает с запасом),
  до 1000 ключей на пользователя суммарно: 990 под записи + 5 под настройки
  `lr_s_*` → максимум 989 записей в облаке.
- Кнопки 📤📥 видны только при согласии ПДн (чекбокс под таблицей);
  🔑 Яндекса в мини-аппе скрыт.
- Удаление ключей в `VKWebAppStorage` отсутствует: при уменьшении базы и при
  отзыве согласия лишние ключи затираются пустой строкой (настройки `lr_s_*`
  отзыв согласия не удаляет — они не ПДн).
- Подключение vk-bridge: локальная копия `vendor/vk-bridge.min.js`
  (`@vkontakte/vk-bridge` 3.0.2), включается в сборку `build/vendor/`.

### Смена версии хостинга: облако вместо миграции

Каждая выкладка хостинга VK — новый stage-URL, т.е. новый origin с пустым
`localStorage`. Переходов между origins больше нет (требование модерации:
в DOM нет `<a href>`, нет и `location.replace` на чужие origins — редирект
на устаревший origin давал в Android-клиенте уход во внешний браузер и
ошибку S3 AccessDenied). Вместо миграции — `VKWebAppStorage`:

- **Настройки** (не ПДн; белый список `LR_LS_KEYS`: религиозный календарь,
  оба согласия, флаг активной пуш-подписки, тема) пишутся в облако ВК под
  ключами `lr_s_<ключ>` при каждом изменении (write-through, `lsSet`) и
  восстанавливаются на запуске для отсутствующих локально ключей — только
  в валидном виде (`applyLsParams`); явная тема из облака приоритетнее
  автозаписи темы при старте.
- **База** хранится в облаке ВК (`"0".."989"`) при согласии ПДн: запись —
  вручную 📤 (`vkDbPut`); на **свежем origin** (детект — по пустоте
  сохранённой ширины колонки `lunarreturns.colw`, НЕ по пустоте базы) при
  согласии база подтягивается из облака автоматически (`vkDbGet`); локальная
  база на свежем origin — заготовка, поэтому диалог объединения не возникает.
- Фолбэк при пустом облаке: открыть прежнюю версию мини-аппа → 📤 →
  вернуться → 📥 (после первого запуска на новом origin автовосстановление
  не повторяется — origin уже не «свежий»).

- Пуши (🔔) в мини-аппе — ВК-нативные уведомления (Web Push в вебвью ВК
  недоступен). Клиент просит разрешение (`VKWebAppAllowNotifications`) и
  отправляет серверу облачной функции только `vk_user_id` (в подписанных
  launch-параметрах — сервер проверяет `sign` защищённым ключом приложения)
  и обезличенные даты MM-DD; имена не покидают устройство. Сервер (та же
  функция Яндекса, действие `vk_subscribe`, хранилище `push/vk_subs.json`)
  шлёт в 09:00 МСК уведомление с общим текстом; по тапу открывается
  приложение и автотап показывает сегодняшний повод.
- Согласие на пуш-подписку — отдельный второй чекбокс (только ВК-режим,
  ключ `lunarreturns.pdPushConsent`): ВК-ид + MM-DD — иной состав данных,
  чем база событий, поэтому согласий два. 🔔 в ВК-режиме виден только при
  этом согласии; его отзыв удаляет подписку из `push/vk_subs.json`
  (действие `vk_unsubscribe`) и гасит ВК-уведомления, базу событий не
  трогая. В веб-режиме второго чекбокса нет: Web Push хранит только
  идентификатор экземпляра браузера.
- **ВК-уведомления не работают в dev/staging-версии**: для «untrusted»
  приложений `VKWebAppAllowNotifications` всегда отвечает отказом
  («Unsupported platform. Notifications are not allowed for untrusted
  apps»). Поэтому чекбокс push-согласия и 🔔 показываются только на
  prod-origin хостинга ВК (`prod-app54746591-…`, флаг `vkProdApp`);
  stage-версии и локальный туннель их не видят. Проверять подписку только
  в production-версии (vk.com/app54746591, выкат с галочкой production в
  workflow деплоя).
- Автотап при каждом открытии (веб и ВК): если сегодня (МСК) есть записи в
  базе — открывается первая совпавшая, между именинниками дня навигируют
  кнопки 🔼🔽 в результате (первый — только 🔽, средний — 🔼🔽, последний —
  только 🔼); иначе при выбранном религиозном календаре и совпадении в днях —
  тап по 🥚 (список дней); иначе — как раньше «луна». Явный `#N` в хэше
  приоритетнее автотапа.
- Подложка и темы (чек-лист ВК): фон `html` — жёлтая как 🌙 `#f7d774`
  (тёмная тема — тёмное золото `#7a6425`), видна при подтягивании за
  верхний край; в мобильном клиенте ВК цвет дублируется через
  `VKWebAppSetViewSettings` (события нет в схеме vk-bridge 3.0.2 —
  вызывается строкой, ошибки глушатся). Тёмная тема — по
  `prefers-color-scheme`; в ВК-режиме приоритет у launch-параметра
  `appearance`/`vk_theme` (класс `theme-dark`/`theme-light` на `<html>`).
  Ручного переключателя нет.
- Pull-to-Refresh (только ВК-режим): подтягивание списка при `scrollY==0`
  тянет контент за пальцем, над ним крутится 🌙; порог ~70px —
  `location.reload()` (подтянуть свежую версию кода после деплоя, не
  выходя из приложения; пункт чек-листа «обновления без выхода»).
  Облако ВК по жесту намеренно не перечитывается — только релоад.
  Диалог вставки 📋 блокирует жест.

## Ограничения хостинга VK

- Не более **24 загрузок** в сутки на приложение.
- Хранится до 10 production- и 100 staging-версий.
- Максимальный размер ZIP-архива — 300 Мбайт.
- Аудио/видео размещать нельзя.

Сервис-воркер (`sw.js`) и PWA-манифест в VK-сборку не входят: в мини-аппе
они не используются (см. `scripts/copy-build.js`), при `vk_app_id` в URL
регистрация SW не выполняется вовсе.
